# Review: web verification of the AgentDesk architecture spine

- Reviewed: `ARCHITECTURE-SPINE.md` (draft, 2026-09-05)
- Lens: every committed decision was web-researched or reality-checked rather than asserted from training data
- Method: npm registry and GitHub release APIs for every Stack row; raw source of x402, OpenZeppelin, ERC-8004, pg-boss, viem, iron-session, and the Binance connector; live JSON-RPC calls to the BSC testnet RPC named in the spine; live REST calls to the Binance Spot Testnet, Spot Demo Mode, and public market-data hosts; official docs for Cloudflare, Zod, and Anthropic. Items the memlog already sourced were re-checked only where the spine uses the fact in a way the memlog did not cover.
- Date of all checks: 2026-09-05

## Verdict

**Conditional pass.** Every version in the Stack table exists and is the current stable release today, and every named service is live and reachable. Two decisions are wrong or under-specified in a way that would break Stage 1 on day 1:

1. **Critical.** The token base contract named in the Stack table and the Structural Seed, OpenZeppelin `ERC20TransferAuthorization`, uses keyed *sequential* nonces. The x402 exact EVM client signs a *random* 32-byte nonce for every payment. Against that contract nearly every `transferWithAuthorization` would revert. The correct base at the same v5.7.0 tag is `ERC3009` from `draft-ERC3009.sol`.
2. **High.** pg-boss 12 `singletonKey` on `send()` is a throttling option. The one-queued-or-active-per-key guarantee that AD-4, AD-5, and the Deferred section rely on comes from a queue *policy* (`exclusive` or `stately`) that the spine does not name.

Both are one-line fixes. The rest of the findings are configuration details the spine should state so the build does not rediscover them.

## Findings

### Critical

**C-1. TUSD must inherit `ERC3009`, not `ERC20TransferAuthorization`.** The spine's Stack row, Structural Seed ("`TUSD` is an OpenZeppelin ERC20 with `ERC20TransferAuthorization` (EIP-3009)"), and Open Questions all name `ERC20TransferAuthorization`. At the v5.7.0 tag that contract is documented as a "variant of ERC-3009 that uses keyed sequential nonces": the 32-byte nonce is split into a 192-bit key and a 64-bit sequence, and `_consumeNonce` calls `_useCheckedNonce`, which reverts unless the sequence equals the next expected value for that key. The x402 client generates `getRandomValues(new Uint8Array(32))` for every EIP-3009 authorization, so the low 64 bits are random and the transfer reverts with probability 1 minus 2^-64. `authorizationState` on that contract also answers a different question (sequence consumed or not), which breaks AD-6's paid-timeout recovery rule. The base class `ERC3009` in `draft-ERC3009.sol`, shipped at the same tag, keeps the standard `_usedNonces[authorizer][nonce]` mapping, exposes `authorizationState(address, bytes32)`, and implements the `(v, r, s)` overload of `transferWithAuthorization` that the x402 facilitator calls for EOA payers. Fix: `contract TUSD is ERC20, ERC3009 { constructor() ERC20("tUSD","tUSD") EIP712("tUSD","1") {} ... }`, update the Stack row, the Seed sentence, and the Open Questions bullet, and keep Circle's `EIP3009.sol` only as the fallback the spine already names.

### High

**H-1. pg-boss singleton semantics need a queue policy.** AD-4 ("publishes `run.execute` with singleton key `workflow_id`"), AD-5 ("`wallet.create` (singleton key `account_id`)"), and Deferred ("pg-boss singleton keys already make a second instance safe") assume `singletonKey` alone guarantees one queued-or-active job per key. In pg-boss 12 the docs list `singletonKey` under throttle options next to `singletonSeconds`; on its own it only scopes a throttle window. The one-per-key guarantee comes from creating the queue with `policy: 'exclusive'` (one queued or active per key) or `'stately'` (one per state per key). Fix: add to the Naming convention row or AD-4 that the four command queues are created with `policy: 'exclusive'` and that `settlement.tick` is registered through `boss.schedule()`. Without this, the DB partial unique index still blocks a second Run row, but a duplicate `wallet.create` would generate a second key for the same account.

### Medium

**M-1. The x402 route config must carry the EIP-712 domain and an explicit asset amount.** `@x402/evm` has no default asset for `eip155:97`, so a `$`-style `price` throws in `getDefaultAsset`. Both the client and the facilitator refuse a 402 whose `extra` lacks `name` and `version`. AD-6 lists scheme, network, asset, and facilitator URL as the shared binding but not `extra`. Fix: add `extra: { name: "tUSD", version: "1" }` to the shared x402 config, require the agent-kit `price` to be an `AssetAmount` built from that config, and publish `extra` on the schema page next to asset and network.

**M-2. Spot Demo Mode fallback is not only a base-URL change.** Demo keys are issued from a regular Binance account's Demo Trading page, not from testnet.binance.vision, and the balances are separate. AD-11's "one-container restart" is right only if a demo key pair already sits in `.env`. Fix: add `EXCHANGE_DEMO_API_KEY` / private key to `.env.example`, provision it on day 1, and have `pnpm doctor` ping both hosts. Also `EXCHANGE_BASE_URL` should be a bare host (`https://demo-api.binance.com`) because the connector's `basePath` appends `/api/v3/...` itself.

**M-3. A stable named tunnel requires a domain on Cloudflare.** The deployment diagram says "named Cloudflare tunnel with a stable hostname"; Cloudflare only issues persistent hostnames for zones the account owns, on the free plan or otherwise. AD-2 makes `PUBLIC_BASE_URL` stability a precondition for any `identity:` intent, so a last-minute quick tunnel would bake a random `trycloudflare.com` host into on-chain `agentURI`s. Fix: list "domain added to Cloudflare DNS" as a day-1 prerequisite next to the submission-format question, and default `agentURI` to the tunnel hostname only after it exists.

**M-4. The facilitator and both x402 clients need `@x402/evm`, not only `@x402/core`.** The AD-1 import diagram draws `apps/facilitator → @x402/core`, `agent-kit → @x402/express`, `adapters → @x402/fetch`. `ExactEvmScheme` lives in `@x402/evm` in three flavours (`/exact/client`, `/exact/server`, `/exact/facilitator`) and `toFacilitatorEvmSigner` is in `@x402/evm`. The Stack table already lists the package; the diagram and AD-1's rule text should too so `no-restricted-imports` does not reject it.

**M-5. The facilitator example cannot run unmodified.** `examples/typescript/facilitator/basic/index.ts` exits without `SVM_PRIVATE_KEY`, hard-codes `baseSepolia`, and registers `eip155:84532`. The Open Questions bullet should say the day-1 check is "the example, with the Solana signer removed and `bscTestnet` + `eip155:97` registered", so the 60-line fallback is not reached for the wrong reason.

### Low

**L-1. pnpm 12 is out and removes flags.** npm `latest` is still 11.25.0, so the spine is current, but 12.3.4 is published under `next-12` and `pnpm self-update` on a teammate's laptop could jump majors. Pin `packageManager` in the root `package.json`.

**L-2. Stack table omits two load-bearing packages.** `iron-session` (9.0.1, ESM-only, Node 22.13+) and `@tanstack/react-query` (5.102.8) are named in conventions and AD-12 without versions.

**L-3. Two Zod majors will coexist.** `@x402/core` and `@x402/evm` depend on `zod ^3.24.2`; the app uses 4.5.4. pnpm isolates them, but `packages/schemas` must import from `zod` 4 explicitly and `z.toJSONSchema` exists only there.

**L-4. Response buffering lengthens the paid request.** `@x402/express` holds the handler's response until `/settle` returns, and the facilitator waits for the receipt. The 15 s paid timeout therefore covers handler (8 s) plus one BSC testnet receipt plus RPC latency; fine at 0.45 s blocks, tight if the RPC degrades. The replay cache in AD-6 already mitigates this; worth a sentence.

**L-5. `agentId` comes from the receipt log.** `register` returns `agentId` only to callers; the worker must decode the `Registered(uint256 indexed agentId, string agentURI, address indexed owner)` event from `eth_getTransactionReceipt`, which works on the official RPC even though `eth_getLogs` does not.

**L-6. Minimum notional is per symbol.** 5 USDT is confirmed for BNBUSDT on both testnet and demo with `applyMinToMarket`; read the `NOTIONAL` filter from `exchangeInfo` rather than hard-coding if other symbols are ever enabled.

**L-7. OpenZeppelin 5.7.0 is on npm under the `dev` dist-tag.** The memlog says it is GitHub-only; `forge install` from the tag remains the right call, this is a note for anyone reaching for `@openzeppelin/contracts` in the TypeScript side.

**L-8. Faucet prerequisite.** The BSC testnet faucet claim requires mainnet BNB on the claiming address (memlog); the day-1 checklist should say so before the Platform Wallet address is generated.
